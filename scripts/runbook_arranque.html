01Antes de tocar nada

Tres comandos que separan "se cayó la app" de "se cayó la red" o "se cayó el ERP". Sin esto se termina reiniciando lo que estaba sano.

02Arranque

Elegí la plataforma. La producción de hoy es Windows; la pista Linux es el mismo docker-compose.yml sobre Docker Engine, y resuelve de raíz el problema del paso 1.

Causa raíz nº 1

Después de un reinicio, nadie levanta nada hasta que alguien inicie sesión

Docker Desktop arranca desde la clave Run del usuario (HKCU\…\CurrentVersion\Run), o sea al iniciar sesión, no al encender la máquina. Y el auto-login está apagado (AutoAdminLogon = 0).

Consecuencia: si se corta la luz y la máquina vuelve sola, el control de accesos queda caído indefinidamente hasta que una persona se siente y loguee como User. Con los contenedores en restart: unless-stopped, todo lo demás se recupera solo — pero recién a partir de ese login.

Hay tres formas de sacarse esto de encima; están en Lo que queda pendiente.

  1. Iniciar sesión en Windows como User

    Presencial o por Escritorio Remoto. No alcanza con que la máquina esté encendida y pingueando: sin sesión iniciada, Docker Desktop no existe.

  2. Esperar a que el motor de Docker esté listo

    Docker Desktop tarda entre 30 y 90 segundos. El ícono de la ballena tiene que quedar fijo y decir Engine running. Si no arrancó solo, abrilo desde el menú Inicio.

    PowerShell
    docker version

    Si dice error during connect, el motor todavía no levantó: esperá y repetí. No sigas hasta que responda.

  3. Levantar la pila

    Un solo comando. compose respeta el orden: primero db, después web —y recién cuando web pasa el healthcheck— todos los pollers.

    PowerShell
    cd C:\Users\User\desarrollo\geba_acs
docker compose up -d

    Es idempotente: si algo ya estaba arriba, no lo toca. Tarda ~40 s por el start_period del healthcheck de web.

  4. Confirmar que están todos

    PowerShell
    docker compose ps

    db y web tienen que decir healthy. El detalle de qué esperar está en Estado esperado.

Ojo con el DEPLOY.md

El DEPLOY.md del repo quedó desactualizado en dos puntos que confunden justo cuando hay apuro: habla del puerto 8000 (hoy compose publica 80) y da 10.0.0.27 como IP de esta PC, cuando 10.0.0.27 es BioStar y esta máquina es la 10.0.0.20. Los comandos de esta página ya están corregidos.

Por qué Linux resuelve el problema

En Linux el demonio de Docker es un servicio de systemd: arranca al bootear, sin sesión de usuario. Con systemctl enable docker y los contenedores en restart: unless-stopped, un corte de luz se recupera solo, sin que nadie toque la máquina.

Esta pista todavía no está probada en el club — es el mismo docker-compose.yml que hoy corre en Windows, con los equivalentes de cada comando.

  1. Verificar el demonio

    bash
    systemctl is-active docker   # debe decir: active
sudo systemctl start docker  # si no lo está

  2. Levantar la pila

    bash
    cd /opt/geba_acs
docker compose up -d
docker compose ps

  3. Dejarlo a prueba de cortes (una sola vez)

    Esto es lo que hace innecesario todo el paso 1 de la pista Windows.

    bash · una vez
    sudo systemctl enable docker

# Y en el BIOS/UEFI: "Restore on AC Power Loss" = Power On,
# para que la máquina vuelva sola después del corte.

  4. El puerto 80 y los permisos

    El contenedor web publica el 80. En Linux eso lo hace el demonio (root), así que no hace falta nada especial — pero sí revisar que no haya un nginx o apache del sistema ocupándolo.

    bash
    sudo ss -lntp | grep ':80 '

  5. Reemplazo del watchdog

    El web_watchdog.ps1 es PowerShell y no aplica. En Linux el equivalente es un timer de systemd que pida la home y reinicie si no hay 200:

    bash · /etc/systemd/system/geba-watchdog.service
    [Unit]
Description=Watchdog del visor geba_acs

[Service]
Type=oneshot
WorkingDirectory=/opt/geba_acs
ExecStart=/bin/sh -c 'curl -fsS -m 20 -o /dev/null http://127.0.0.1/ \
  || docker compose up -d web'
    bash · geba-watchdog.timer + activar
    [Unit]
Description=Chequeo del visor cada 5 min

[Timer]
OnBootSec=3min
OnUnitActiveSec=5min

[Install]
WantedBy=timers.target
    bash
    sudo systemctl daemon-reload
sudo systemctl enable --now geba-watchdog.timer

Todo lo demás —estado esperado, verificación, fallas conocidas— es idéntico en las dos plataformas, porque lo que corre adentro de los contenedores es el mismo Linux.

04Verificación punta a punta

Que los contenedores estén "arriba" no quiere decir que un socio pueda entrar. Estas cinco pruebas recorren la cadena completa.

  • La app responde. curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1/ devuelve 200.
  • Entran pasos en vivo. El log del poller muestra líneas +N ingresos cuando alguien cruza un molinete.
  • La cadena está consistente. El chequeo de consistencia sale con código 0.
  • El visor del puesto pinta. Desde una PC de molinetes, http://10.0.0.20/xsys/puerta/ muestra las columnas con foto, mensaje e ícono de rostro o credencial.
  • Un paso real abre. La prueba que vale: que alguien pase la credencial o la cara y el molinete gire.
las dos primeras, en vivo
docker compose logs --tail 20 poller
docker compose logs --tail 20 web
auditoría xSys ↔ espejo ↔ BioStar
# --rapido: no recalcula contra xSys, mide frescura y BioStar. ~segundos.
docker compose exec web python manage.py acs_consistencia --rapido

# Informe completo (más lento, recalcula socio por socio contra el ERP).
docker compose exec web python manage.py acs_consistencia

El comando devuelve exit 1 si encuentra divergencias: dice, con números, si alguien puede pasar sin poder o no puede pasar pudiendo, y en qué eslabón se rompió. Después de una caída larga es normal que la lista blanca esté vieja; se corrige sola en la próxima barrida (15 min). Si querés forzarla:

forzar puesta al día
docker compose exec web python manage.py xsys_whitelist_full --push-biostar
docker compose exec web python manage.py xsys_sync

05Si Docker no levanta

El repo trae un modo nativo, sin Docker: waitress sirviendo en el puerto 80 y el poller de CD_ES como procesos de Python, registrados como Tareas Programadas que arrancan con Windows.

Estado hoy

Las tareas GEBA-ACS-Web y GEBA-ACS-Poller existen pero están Disabled desde el 21-07-2026, cuando se pasó a Docker. Su último resultado fue un error (267014 = "la tarea no está corriendo"), coherente con haberlas apagado.

Es un bote salvavidas, no un modo paralelo: cubre solo web y poller. No corren el sync, la lista blanca, las fotos, el facial ni la deuda. Sirve para que el molinete abra mientras se arregla Docker; no para quedarse ahí.

Encenderlo

PowerShell como Administrador
# Docker y el modo nativo pelean por el puerto 80: bajar Docker primero.
cd C:\Users\User\desarrollo\geba_acs
docker compose stop web

Enable-ScheduledTask -TaskName "GEBA-ACS-Web","GEBA-ACS-Poller"
Start-ScheduledTask  -TaskName "GEBA-ACS-Web"
Start-ScheduledTask  -TaskName "GEBA-ACS-Poller"

Get-ScheduledTask GEBA-ACS-* | Get-ScheduledTaskInfo

El modo nativo usa el .venv del repo y el mismo .env, pero pega contra un Postgres que tiene que estar accesible. Si el que cayó fue justamente el contenedor db, este camino no te salva: ahí lo que hay que levantar es db.

Volver a Docker

PowerShell como Administrador
Stop-ScheduledTask    -TaskName "GEBA-ACS-Web"
Stop-ScheduledTask    -TaskName "GEBA-ACS-Poller"
Disable-ScheduledTask -TaskName "GEBA-ACS-Web","GEBA-ACS-Poller"

cd C:\Users\User\desarrollo\geba_acs
docker compose up -d

Dejarlas deshabilitadas no es opcional: si arrancan solas en el próximo reinicio, se quedan con el puerto 80 y el contenedor web no puede bindear.

06Fallas conocidas

Cada una de estas ya pasó en este sistema. La columna del medio es lo que realmente la causa, que casi nunca es lo que el error dice.

SíntomaCausa realQué hacer
La máquina está prendida y pinguea, pero nada responde en el 80 Nadie inició sesión en Windows. Docker Desktop no arrancó. Loguearse como User. Ver paso 02.
web reinicia en loop: entrypoint.sh: bad interpreter Git convirtió el .sh a CRLF al clonar en Windows. git config --global core.autocrlf false y volver a clonar.

07Lo que nunca hay que hacer

Destructivo

docker compose down -v

La -v borra el volumen geba_acs_postgres_data, que es todo el espejo local: socios, fotos, lista blanca, historial de accesos. Recuperarlo es correr xsys_init de cero, que tarda horas y deja los molinetes sin lista blanca mientras tanto.

Para bajar todo sin perder datos: docker compose stop. Para bajar y borrar contenedores conservando el volumen: docker compose down — sin la -v.

  • No cambies POSTGRES_USER / PASSWORD / DB en el .env. Postgres los aplica solo cuando el volumen está vacío; cambiarlos después rompe el login sin avisar por qué.
  • No levantes los servicios intelektron-* "para que estén todos". Están apagados por decisión, no por olvido.
  • No corras el modo nativo y Docker a la vez. Se pelean por el puerto 80 y el ganador es impredecible.
  • No pares un contenedor a mano y te vayas. unless-stopped respeta el freno para siempre; así fue como el visor quedó cinco horas caído el 18-08-2026.

08Lo que queda pendiente

Tres cosas que hoy hacen falta y que este runbook no puede resolver, porque son decisiones, no comandos.

1 · Que el sistema vuelva solo después de un corte

Hoy depende de que una persona inicie sesión. Tres caminos, de menos a más trabajo:

  • Auto-login de Windows (AutoAdminLogon=1). Es el cambio más chico y arregla el problema entero. A cambio, la máquina queda con una sesión abierta sin contraseña: hay que evaluarlo con el criterio de seguridad del club.
  • Registrar el modo nativo al arranque con scripts\register_native_services.ps1. Las tareas usan S4U, así que corren sin sesión iniciada. Pero solo levanta web y poller — el resto de la pila sigue esperando el login.
  • Mover a Linux. Es la solución de fondo: systemd arranca Docker al bootear y el problema desaparece. Ver la pista Linux del paso 02.

2 · El watchdog está escrito pero no registrado

scripts\web_watchdog.ps1 chequea el puerto 80 cada 5 minutos, levanta web con docker compose up -d si no responde y avisa por mail el cambio de estado. Existe justamente porque el 18-08-2026 el visor quedó cinco horas caído sin que nadie se enterara. No hay ninguna tarea registrada que lo ejecute. Para activarlo:

PowerShell como Administrador · una vez
cd C:\Users\User\desarrollo\geba_acs
powershell -ExecutionPolicy Bypass -File scripts\register_web_watchdog_task.ps1

Get-ScheduledTask -TaskName "GEBA-ACS-WebWatchdog" | Get-ScheduledTaskInfo

El mail necesita WATCHDOG_SMTP_HOST, _USER y _PASS en el .env (una app password de 16 caracteres, no la clave de la cuenta). Sin eso el watchdog igual levanta el visor: solo no avisa. Para frenar el auto-levantado durante un mantenimiento, crear el archivo web_watchdog.pause en la raíz del repo y borrarlo al terminar.

3 · Hay un cambio sin commitear

El docker-compose.yml tiene 56 líneas sin commitear que agregan deuda-actividades. Mientras estén solo en el disco de esta máquina, un git clone en otro lado —o una restauración— levanta la pila sin ese servicio, y los socios que pagan la deuda de actividades siguen rebotando en el molinete. Conviene commitearlo.

Cómo se armó esto. Los datos salen de la máquina de producción el 10-09-2026: docker compose ps, Get-ScheduledTask, el docker-compose.yml vigente, el .env (sin secretos), la clave Run de Docker Desktop y Winlogon. No es una copia del DEPLOY.md — donde los dos difieren, manda lo que se midió en la máquina.

Alcance. Cubre levantar el sistema, no instalarlo de cero: se asume que el repo, el .env y el volumen de Postgres ya existen. Para una instalación nueva, DEPLOY.md (corrigiendo puerto e IP) y el paso 6, xsys_init.

Sin probar. La pista Linux está derivada del compose real, pero no se ejecutó en ningún servidor del club.
